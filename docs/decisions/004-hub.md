# ADR-004 :: Hub Mac

Last updated: `2026.11.21`

> One always-on Mac is the hub. It keeps every recording, runs all
> transcription, keeps a catalog in SQLite, and serves an HTTP API on the
> user's Tailscale network. Other Macs and the iPhone are clients: they upload
> finished recordings and read transcripts back. This replaces the iCloud
> hand-off of [ADR-002](002-ios-capture-companion.md).

## 1. Decision

- The hub is a Mac that is always on, such as a Mac mini. It runs the same
  `quill` binary with `hub.serve: true`.
- The hub serves the API in [hub-api.md](../hub-api.md) on `127.0.0.1` only.
  `tailscale serve` publishes it to the tailnet with HTTPS. There is no other
  authentication: the tailnet is the boundary.
- A client uploads each finished recording (its segment files, then a commit
  with `meta.json`) and reads the session and its transcript back. Clients are
  a Mac running `quill` with `hub.url`, and the iPhone app.
- Only the hub transcribes. It uses the existing transcription queue and
  engines ([ADR-003](003-remote-transcription-server.md)). A client that can't
  reach the hub keeps the recording and tries again later. It never
  transcribes locally.
- The hub keeps a catalog of sessions in SQLite
  (`~/Library/Application Support/quill/hub.sqlite`). A hub-wide revision
  counter lets a client ask for everything that changed since the last
  revision it saw.
- The session folders stay the source of truth for content. Each folder on
  the hub has a `.hub.json` file with the session id and the device that sent
  it. The hub rebuilds the catalog from the folders at every start.

## 2. Rationale

- **iCloud Drive proved unreliable on a headless Mac.** On the Mac mini, the
  iPhone app's iCloud container returned "Resource deadlock avoided" for its
  folders. Recordings stopped arriving, and nothing reported the failure to
  the user or in a log.
- **The iCloud design supported only one Mac.** The container was a hand-off
  between one iPhone and one Mac. A second Mac (a MacBook used in meetings)
  had no place in it.
- **An API gives one place for features to come.** Search, speaker names, and
  summaries need one copy of the archive and one place to compute on it.
  A request that fails gets an answer and an error code, so failures can be
  seen and retried.
- Tailscale already connects the user's devices and the transcription server.
  `tailscale serve` adds HTTPS without certificates to manage.

## 3. Design implications

- Recordings now leave the device they were made on, but only for a Mac the
  user owns, over the user's own network. "Local-only" in the shared contract
  means the user's own devices and network, as in ADR-003.
- The catalog is an index. Deleting `hub.sqlite` loses nothing: the hub
  rebuilds it from the folders, with the same session ids from each folder's
  `.hub.json`. The rebuilt catalog gets a new catalog id and starts its
  revision counter again. The list answer carries the catalog id, so a client
  sees that it changed, discards its cache, and reads everything again from
  revision 0. Schema changes go through a versioned migrator, so
  tables can be added later.
- A commit makes the staged folder complete (`meta.json`, `.hub.json`) before
  one rename puts it in the recordings folder. A folder there is always
  complete, so a crash before its catalog row is recovered with the right id.
- A client stores the session id next to the recording before the first
  upload, and reuses it on every retry. Uploads replace earlier attempts and a
  repeated commit returns the same session, so every step is safe to repeat.
- The hub can't transcribe or answer while it is off or asleep. It must be
  always on, with sleep disabled.
- The API has no authentication. Anyone on the tailnet can read every
  recording. The hub must never be published outside a private network.

## 4. When to Revisit

Reconsider if the tailnet is shared with people who should not read the
recordings (add authentication then), if more than one person records into
the same hub, or if the iPhone needs to work fully offline for long periods.
